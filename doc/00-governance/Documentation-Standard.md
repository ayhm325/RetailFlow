# معيار إدارة التوثيق

## 1. الغرض

إنشاء مصدر معرفة تقني واحد يتبع النظام الفعلي، ويفصل الحقيقة المنفذة عن الهدف المستقبلي والتجربة والافتراض. تُحفظ الوثائق بجانب الكود في Version Control، وتُحدّث ضمن نفس Pull Request الذي يغيّر السلوك أو العقد أو البيانات.

## 2. ترتيب موثوقية الأدلة

عند التحقق من ادعاء تقني، استخدم الترتيب الآتي:

1. **الكود الفعلي** في commit محدد، بما في ذلك التسجيل في DI، middleware، endpoint mapping، entities، configurations وmigrations.
2. **الاختبارات القابلة للتشغيل** التي تثبت سلوكاً محدداً، مع اسم الاختبار والبيئة.
3. **إعدادات البناء وCI** لإثبات ما يُبنى وما يُختبر، لا لإثبات نجاح كل تشغيل.
4. **المعايير الرسمية** لتحديد ما ينبغي فعله، وليس ما نفّذه المشروع.
5. **مراجع الخبراء** لتحسين أسلوب توثيق المعمارية والقرارات.

README سابق أو ملف تخطيط لا يُعتبر دليلاً على التنفيذ. ولا تُستنتج ميزة من وجود DTO أو enum فقط؛ يجب تتبع endpoint ثم service ثم persistence والاختبارات.

## 3. وسوم الأدلة داخل الوثائق

يجب أن يكون لكل ادعاء مهم مسار كود أو اختبار. تُستخدم الوسوم:

- `CODE:` مسار أو أكثر إلى التنفيذ.
- `TEST:` اسم ملف/اختبار يثبت سلوكاً.
- `CI:` خطوة في Workflow.
- `STANDARD:` مرجع معياري خارجي.
- `OPEN:` سؤال أو نقص لم يُحسم.

مثال: `CODE: src/RetailFlow.Api/Orders/CustomerOrderEndpoints.cs`.

## 4. دورة حياة الوثيقة

| الحالة | المعنى |
|---|---|
| Draft | قيد المراجعة، لا يعتمد كالتزام منتج |
| Reviewed | راجعه شخص تقني، ولم يُعتمد بالضرورة من مالك المنتج |
| Approved | اعتمده صاحب صلاحية المنتج/الهندسة |
| Superseded | استُبدل بإصدار أو ADR أحدث |

كل وثيقة مهمة يجب أن تحتوي عنواناً، الحالة، تاريخ التحديث، baseline commit، المالك الوظيفي، روابط الأدلة، والقرارات المفتوحة.

## 5. متى يجب تحديث الوثائق؟

- إضافة أو تغيير endpoint أو DTO أو authorization policy: حدّث API وSecurity وTraceability.
- تغيير Domain invariant أو state transition: حدّث Domain والـ lifecycle والاختبارات.
- تغيير Entity/Configuration/Migration: حدّث Data Dictionary وDatabase وMigrations.
- تغيير Middleware أو Authentication أو session: حدّث Security وRuntime flow وOperations.
- تغيير pipeline أو SDK أو deployment configuration: حدّث CI وOperations.
- قرار معماري ذو أثر طويل: أضف ADR جديداً؛ لا تعدّل ADR قديماً ليبدو وكأنه اتخذ قراراً مختلفاً تاريخياً.

## 6. قواعد الصياغة

1. لا تستخدم ألفاظاً مطلقة مثل Secure أو Atomic أو Production-ready دون دليل وحدود واضحة.
2. ميّز بين `behavior implemented` و`behavior verified`.
3. لا تعتبر `experiments/` جزءاً من المنتج الأساسي.
4. لا تنشئ FR أو BR على أنها متطلبات معتمدة؛ يمكن إنشاء معرفات `OBS-*` لوصف ما لوحظ في الكود.
5. لا تضع أسراراً أو connection strings حقيقية أو بيانات عملاء في الوثائق.
6. لا تنسخ مفاتيح OWASP/ASVS من الذاكرة؛ راجع الإصدار الرسمي عند تحديث مصفوفة الامتثال.

## 7. مبادئ المراجعة

كل تغيير توثيقي يمر بمراجعة: دقة المسارات، اتساق أسماء الأدوار والحالات، تزامن API مع الكود، صلاحية Mermaid، عدم تسويق Open Decisions كحقائق، وعدم الادعاء بالامتثال دون Verification Evidence.

**المراجع المنهجية:** C4 Model، وArchitecture Decision Records لدى DfE/Thoughtworks. راجع `11-references/Standards-and-References.md`.
